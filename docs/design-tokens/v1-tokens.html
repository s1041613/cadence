Elevation 只有兩階，而第一階是「不用陰影」。躺在頁面上的東西（卡片、月曆格、segmented、按鈕）靠 --cd-line 和表面色區分，不用陰影。只有真正浮起來蓋住頁面的才有。

一個 overlay 值就夠，因為每個浮層都配 --cd-scrim，而 scrim 才是在講「我蓋住頁面了」——陰影只負責收邊，這件事不隨元件變。

沒有垂直偏移是刻意的：底部 sheet 貼齊視窗底緣，向下投射會被裁掉，等於沒陰影。

不受色盤控制使用者資料

這些值會被寫進資料庫的事件記錄，所以必須是字面 hex——寫 var() 等於把 CSS 語法存成資料。

類別值真實來源
象限四色 src/composables/use-theme.ts
事件預設色盤 CdAppearancePicker.vue 的 COLOR_SWATCHES
事件預設色#E3A75C同上
已知後果：既有事件記錄存著舊 hex，換色盤不會回溯更新它們，所以舊事件與新事件會不一致。那是資料遷移問題，不是 token 問題。

兩條規則

1. 任何會被半透明使用的角色，必須提供 -rgb 通道值。
--cd-ink-rgb · --cd-accent-rgb · --cd-scrim-rgb

字面的 rgba(86, 88, 94, .06) 跟任何 token 名稱都沒有共同文字，所以改名時會回報成功、值卻凍結在舊色盤。這正是整個 token 工程要防的失敗——而它先前對全站最常用的顏色完全沒有防護。
2. 名字描述角色，永遠不描述材質或呼叫點。
測試：如果色盤或版面變了，這個名字還會是真的嗎？

--cd-olive 在 accent 改色的那一刻就開始說謊；--cd-topbar 的 17 個消費者裡只有 1 個是 topbar。這是 v2 作者看著舊名字會卡住的原因。
護欄：npm run check:tokens 有 6 條規則，任何硬編碼的色盤值會讓它失敗——包含最難抓的 rgba() 三元組形式。
