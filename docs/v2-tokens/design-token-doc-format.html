Design Token 文件：業界做法與建議

回答「一般 design token 文件長怎樣」以及「怎麼定義才能讓 AI 或工程師讀懂並套用」
所有數字都經過實測驗證，非估計
研究過程中發現一件比格式選擇更急迫的事：你的四個顏色來源已經不同步了，不是「將來可能會」。

細節見「先修的資料問題」節。建議先解那個，再談工具。

建議：DTCG JSON 當唯一來源 + Style Dictionary 產生四個輸出

用 DTCG JSON 作為唯一手寫來源，由 Style Dictionary 產生 CSS custom properties、Tailwind @theme、Sass 變數。分兩階段做，第一階段的價值就已超過成本。

一次性成本
2–4 小時
104 個 token 翻成 JSON，$description 要人寫
新增依賴
1 個
style-dictionary，devDependency，不進 bundle
每次改 token
淨省時間
從改 1–4 個檔變成改 1 個 JSON

為什麼不是其他選項

方案為什麼不選
維持現狀
純 CSS 手動同步		今天能跑，但已經分歧了（見下節），證明人類 review 抓不到。真正的成本轉折點是換色盤那天 —— 同步成本會從四個地方變成八個。
CSS 當源頭
寫 script 產生其他三個		解決同步問題，但不解決可讀性問題。CSS 沒地方掛 $description、$type、對比契約、「不要直接引用」標記 —— 而這些正是你要的核心。CSS 也表達不了 composite type（一個 shadow 是四個可分別驗證的數值，不是一個字串）。
Tokens Studio
Figma plugin 當源頭		它解決的是設計師與工程師的交接問題，你是一個人，設計決策在你腦裡。多一個 plugin 只是多一層要同步的東西。除非哪天有設計師加入。
Style Dictionary 但用舊格式少一層規格包袱，但 DTCG 是 AI agent 最可能認得的格式，而「讓 AI 讀懂」是你的明確需求。DTCG 並沒有比較難寫。

分兩階段

Phase 1（現在做）：JSON 當來源，只產生 CSS + Tailwind + Sass。
  • use-theme.ts 的四象限色先不動，維持手寫 hex（理由見「AI 推不出來的事」）。JSON 裡標註它是 mirror，用 lint 檢查兩邊一致，而不是產生它。
  • 產出檔標上 DO NOT EDIT 並進 git —— solo 專案不該讓 npm run dev 依賴額外步驟才看得到顏色。
  • 這一階段解決的是已經壞掉的東西。
Phase 2（等 rename 和 data-theme 要做時再做）：semantic tier、role-based 命名、第二套 palette。 不要現在做 —— rename 本來就還沒定案，把兩件事綁一起會讓兩件都做不完。

什麼情況我會改口說不要做

如果四個來源只有一個（純 CSS），而且沒有換色盤計畫，那 DTCG 就是過度工程，寫一份 markdown 說明就夠了。但你不是這個情況。

業界格式概覽

三個你會遇到的名字，以及它們的關係

DTCG（Design Tokens Community Group）JSON

規格狀態要講清楚：它是 Community Group Draft Report，不是 W3C Recommendation，也沒走 W3C 標準流程。 實務上已是事實標準（Style Dictionary、Tokens Studio、Figma Variables export 都支援），但規格仍在演進。 
{
  "color": {
    "ink": {
      "$type": "color",              // 型別，可在 group 層宣告並被子節點繼承
      "$value": "#56585E",
      "$description": "…",           // 人類與 AI 讀的說明
      "$extensions": {               // 自訂 metadata，規格保證不干涉
        "com.cadence.tier": "primitive"
      }
    },
    "body": {
      "$value": "{color.ink}",       // alias：大括號 + 點分路徑
      "$type": "color"
    }
  }
}

要點

  • $ 前綴是規格保留字。沒有 $ 的 key 一律視為 group 或 token 名。
  • $type 可繼承 —— 在 group 上寫一次，底下全部適用。對可讀性幫助很大。
  • Alias 是 {group.token}，整個 $value 就是那個字串，不能做 "{color.ink} 2px" 這種內插。
  • Composite types：shadow、typography、border、gradient、transition、strokeStyle。$value 是物件而非純量 —— 這是 CSS 做不到的表達力。
一個要自己驗證的細節：2025.10 draft 的 dimension 是物件形式 { "value": 8, "unit": "px" }。 純字串 "8px" 在該版是否仍合法，研究時無法確定 —— 實作時請對照 Style Dictionary 5.5.0 的實際 parser 行為，不要照抄範本。

Style Dictionary

Node build tool。讀 token 檔（JSON / JSON5 / YAML），跑 transform，輸出任意格式。

項目說明
版本v5.5.0（2026-06-21 發布）
DTCG 支援2025.10 的 color / dimension 支援落在 5.3.0 / 5.4.0（2026 年 2–3 月）
啟用方式usesDtcg: true —— 開了才會讀 $value/$type 而非舊格式的 value/type
內建 formatcss/variables、scss/variables、javascript/es6 等
自訂 format一個回傳字串的函式。寫 Tailwind @theme block 大概二十行

Tokens Studio

Figma plugin，把 token 存在 Figma 裡，可 export 成 DTCG JSON 或 sync 到 git。

它的定位是設計師端的編輯介面，不是 build tool —— 和 Style Dictionary 是上下游關係，不是替代關係。 原生格式和 DTCG 有出入（歷史上用 value/type，並有 $themes.json 這類自有檔案），需要轉換。

對這個專案：不要用。

什麼讓 token 文件對 AI 和新工程師可讀

這是你問題的核心。以下依權重排序，前三項貢獻了大部分價值
1
單一真實來源，其餘皆為產物且標記為產物
其他所有事都建立在這之上。如果有四個手寫來源，$description 寫得再好，AI 讀了其中一份仍然會改錯地方。 產出檔第一行必須是 /* AUTO-GENERATED … DO NOT EDIT. */。

AI agent 對 DO NOT EDIT 的遵從度很高，這一行的投報率是全部裡最高的。 反過來說，沒有這一行的產出檔比手寫檔更危險 —— 它看起來可以改。
2
$description 寫「何時用」而非「這是什麼」
最常被寫壞的欄位，也是新工程師與 AI 唯一能讀到「意圖」的地方。
✗ 沒有資訊量（重述了 $value 已說過的事）
"The olive accent color, #B3AC91"
✓ 有資訊量（適用場景、邊界、誤用後果）
"Primary accent. Use for interactive affordances that are not the primary CTA. Do NOT compose translucent washes from this token — use olive-rgb inside rgba() instead, so the wash follows a palette swap."
判準：把 $value 遮住，這段描述還能讓人知道該不該用它嗎？不能的話就是廢話。 好的描述要有：適用場景、不適用場景（負面資訊常比正面更有用）、誤用的後果。
3
明確的 $type，包含 composite type
"0 1px 3px rgba(86,88,94,.06)" 對機器是一個字串；標上 $type: "shadow" 加結構化 $value 之後，它是四個可分別驗證、可分別 transform 的欄位。

AI 要改「陰影再淡一點」時，前者要做字串解析（容易改壞），後者只改 color.alpha。 你有 12 個 shadow token 全是字串形式 —— 這是 composite type 最直接的收益處。
4
機器可檢查的約束（要能執行，不能只是散文）
寫在註解裡的規則會被無視；寫成能 fail build 的檢查才會被遵守。 你的 check-tokens.mjs 已經證明這模式有效。

把約束放進 $extensions 讓 lint 讀它，而不是把規則 hardcode 在 lint script 裡 —— 否則你只是把四來源同步問題搬到 lint 上。 
"$extensions": {
  "com.cadence.forbid-literal": ["#B3AC91", "rgba(179, 172, 145"],
  "com.cadence.contrast": { "against": "{color.surface.default}", "min": 4.5 }
}
5
明確的 tier 標記與「不要直接引用」
AI 特別需要這個。給它一份平坦的 104 個 token 清單，它會挑名字看起來最像的那個，而不管 tier。 明確寫 "direct-use": "forbidden" 加上指出替代品，命中率會顯著提高。

注意：Phase 1 還沒有 semantic tier（命名仍是 material-bound），所以現在全部標 primitive 並誠實註明「semantic tier 尚未建立」。 不要假裝有 tier 制度 —— 假的結構比沒有結構更糟，AI 會照著假結構推論。
6
對比契約寫明配對
「這個顏色對比夠嗎」沒有答案，「這個顏色配 surface.default 是 4.8:1」才有。 你的 token 檔已經有這個直覺（每個象限 fill 都有 ink 夥伴）。把它從註解升級成機器可讀欄位就能自動驗證。
7
穩定的命名結構
重要，但排最後 —— rename 尚未定案，而且前六項不依賴命名就有價值。 不要為了做 token 檔而順手改名，那是兩個獨立的變更。

    "title": {
      "$value": "{font.ui}",
      "$description": "DEPRECATED alias. Despite the name it maps to the UI face, NOT the

注意最後那個 description。它不重述值，而是說明何時用、邊界在哪、以及為什麼看起來像 bug 的東西其實是對的。 這種描述對 AI 的價值遠高於「這是 Zen Kaku 字體」。

AI 光讀 token 檔推不出來的事

這一節防止「AI 讀完 token 檔就動手，然後全做錯」
建議放在 tokens/_meta.json，並在 CLAUDE.md 放一份對應段落 —— 因為 AI agent 讀 CLAUDE.md 的機率高於讀 token 檔。

1. CdMonthGrid.vue 的 JS 鏡像

const CELL_METRICS = {
  desktop: { cellPad: 16, headGap: 3, headH: 26, chipH: 24.5, chipGap: 2 },
  phone:   { cellPad: 6,  headGap: 1, headH: 22, chipH: 25,   chipGap: 2 }
} as const

用來算一格月曆塞得下幾個事件晶片。改 CSS 而不改這裡不會壞、不會報錯、不會有 type error —— 只會安靜地算錯排版。

機器讀 token 檔完全看不到這層耦合，因為這些數字在 CSS 裡根本不是 token（padding: 16px、height: 26px 散在 style block 裡）。

必須寫下：這些值是 token 的 consumer。若把它們 tokenise，CELL_METRICS 必須從產生的 JS token 匯入，不能繼續手抄。在那之前，任何改動 month cell 幾何的 PR 都必須同時檢查這個常數。

2. 象限色會 persist 到資料庫

use-theme.ts 的四個 backgroundColor 會被寫進 event record 存進資料庫。

必須寫下：這四個值必須維持 literal hex。放 var(--cd-olive) 會把 CSS 語法當資料存進 DB，讀回來是壞掉的字串。

還有一個更隱蔽的：已經存進 DB 的舊記錄帶著舊 hex，所以改這四個值不會回溯更新既有資料 —— 換色盤會讓新舊 event 顏色不一致。這是 migration 問題，不是 token 問題。

因此 Phase 1 不要由 generator 產生 use-theme.ts。正確做法是 lint：檢查 QUADRANTS 的 hex 與 token 檔一致，不一致就 fail。保住同步性又不動 persist 契約。

3. Tailwind 與 Sass 的 build-time 天花板

兩者都不能讀 runtime CSS custom property。Tailwind v4 的 @theme 需要 build 時的具體值；Sass 變數在編譯期就消失了。

必須寫下：這兩個檔案是 data-theme 切換的天花板。未來加第二套 palette 時， var(--cd-*) 會跟著換，但任何 Tailwind utility class 和任何 Sass 變數會凍結在 build 時那套值上。

機器讀 token 檔完全看不出這個限制 —— 只會看到三個檔案有相同的值，以為它們等價。

4. Zen Kaku 沒有 600 也沒有 800

字重目前用量狀態
600123 處字體沒有，瀏覽器合成
80011 處字體沒有，瀏覽器合成
這已經是實際的 bug，不是預防性提醒。合法 weight 只有 300/400/500/700/900。

AI 讀 token 檔看到 --cd-font-ui: 'Zen Kaku Gothic New' 完全不會知道這件事 —— font family token 不帶 weight 資訊。這正是 $extensions.available-weights 存在的理由， 而且應該有一條 lint 規則掃 font-weight: 600|800。

5. 兩個額外發現

  • --cd-bp-desktop: 900px 是假 token。CSS 變數不能用在 @media query，真正生效的值在 breakpoints.sass。機器會以為改它就能改斷點。
  • --cd-olive-mix-2（#6E6A52）與 -mix-3（#6E6A54）差 2 個藍階，肉眼不可分。這是未解決的重複，不是設計意圖 —— 要標註，否則 AI 會嘗試為兩者發明不同的語意角色。
