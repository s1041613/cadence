分層模型

目前是單層。下面描述的是現況與目標的差距。
現況：所有 token 都在同一層。--cd-olive 既是原始色值也是語意角色，沒有區分。 這在只有一組配色時沒問題，但要支援第二組時會出現「換 theme 該覆寫哪些」的模糊地帶。

目標三層

Tier 1 — Primitive 未實作

原始色階，元件永不直接使用。存在的意義是把「這幾個角色其實是同一個顏色」講明白一次。

--cd-p-warm-500: #9C9E94;   /* 目前被 --cd-muted 和 --cd-ink-3 共用 */

前綴 --cd-p-* 刻意設計得醜，讓誤用在 code review 時肉眼可見，不需工具。

Tier 2 — Semantic（角色） 現況等同這層

元件唯一該碰的層。換 theme 只覆寫這一層。

目前的 --cd-* 全部落在這層，但名字多半綁材質而非角色，所以還不算真正的語意層。

Tier 3 — Alias（過渡） 字體已有，顏色未做

讓舊名稱在遷移期間繼續運作，用完即刪。字體部分已經實作：

--cd-font-title: var(--cd-font-ui);
--cd-font-mono:  var(--cd-font-ui);
--cd-font-serif: var(--cd-font-display);
不做 component 層。42 個 Cd* 元件會生出約 120 個只有間接性的 token。 加它的時機很具體：當某個 theme 需要只改一個元件而不動它讀的角色時。目前沒有這個需求。

命名規則

現有 token 多數不符合這些規則。這是改名時要遵循的目標，不是現狀描述。

規則 10 的測試法

如果配色或版型變了，這個名字還成立嗎？--cd-month-paper 同時綁定材質（paper）和畫面（month）—— 換配色會變假，月曆改版也會變假。

Ink 文字色

4 個 token，legacy 共 169 處使用 —— 最大的族群。
Token值Legacy對比（於 #FBFAF7）用途
--cd-ink#56585E687.02:1主要文字
--cd-ink-2#6E7176345.13:1次要文字
--cd-muted#9C9E94632.60:1弱化文字
--cd-ink-3#9C9E9442.60:1與上一列同值
兩個問題。

1. --cd-muted 和 --cd-ink-3 是同一個值的兩個名字。 檢查過 4 個 ink-3 使用點，跟 63 個 muted 使用點沒有語意差別 —— 只是不同時期不同作者取了不同名。 兩個名字對一個角色是純粹的負債：它讓 theme 作者要定義兩次，而且遲早會不小心分歧。 建議合併，而且 ink-3 只有 4 處，是最便宜的遷移。

2. 這個值不符合 WCAG AA。2.60:1 遠低於 4.5:1 門檻，影響 67 個使用點。 但這次不改 —— 改它會動到 67 處渲染，該獨立成一次可審查的變更。 #7E8175 可以達標且保留暖橄欖調性。

缺少的角色

目前沒有 --cd-ink-on-accent 這種「放在深色填色上的文字」的通用角色 —— 只有四象限有配對 ink。--cd-olive-ink 實質上扮演這個角色但名字綁材質。

5 個 token，legacy 共 66 處。使用高度集中在第一個。
Token值Legacy對比建議

--cd-line-5 建議刪除。只有 1 個使用點，而且和 --cd-line 只差 0.02 對比 —— 肉眼完全分不出來。 留著它會逼未來每個 theme 都要發明第五個沒有意義的線條值。

--cd-line-3 建議保留，雖然零使用。理由跟上面相反：它補完了一個連貫的 4 階梯度（faint < soft < line < strong）， 而有缺口的階梯會誘使人硬寫。
全部線條色都達不到 3:1 的非文字 UI 對比建議。 純裝飾性分隔線可以接受，但當線條是互動元件唯一的邊界指示時就不行（例如未聚焦的輸入框）。 v1 在表單欄位上違反這點。已記錄，這次不改。

本次修正：17 處隱形的硬寫

改動前有 17 處寫成 rgba(179, 172, 145, α)。這些對改名完全隱形 —— 它們跟 --cd-olive 沒有任何文字關聯，搜尋 token 名稱找不到， 所以「把 token 改名」做完後會以為完成了，切換時才發現底色還是暖的。

現在全部改成 rgba(var(--cd-olive-rgb), α)，alpha 值逐一保留，渲染完全相同。

為什麼 accent 不能收斂成一個 token

角色對比契約v1 是否達標

四個配對文字色是本次新增的 CSS token。它們原本只存在於 TypeScript，CSS 層完全構不到。 四組配對全部通過 AA（4.68 到 6.19），是整個 schema 裡對比表現最好的族群。
權威在 TypeScript，不在 CSS。 src/composables/use-theme.ts 是這些顏色的真實來源，而且必須保持字面 hex —— 因為 backgroundColor 會經由 completePromotion() 寫進事件記錄的資料庫。 如果改成 var(--cd-quad-do)，存進去的會是字串 "var(--cd-quad-do)"， 任何非 CSS 的消費者（對比計算、匯出、Email）都無法解析。

所以 CSS 這邊是鏡射，兩邊都寫了交叉註解。這是刻意的重複，方向正確（資料層為權威）。

換 theme 時的建議

四象限色建議保留彩色，視為語意資料色而非 chrome。去彩度後事件將只能靠位置和文字區分，失去分類法的視覺意義。

陰影的 theme 策略

陰影幾何固定、只換色調。v1 用了兩種色調：rgba(86,88,94,α)（等於 --cd-ink 的 RGB）和 rgba(40,38,30,α)（暖灰）。兩者在中性配色下都會變成色偏而非深度感。

/* 目標形式：theme 只覆寫兩個三元組，而非 12 個完整陰影 */
--cd-shadow-tint-rgb: 40, 38, 30;
--cd-shadow-drawer: -22px 0 52px -22px rgba(var(--cd-shadow-tint-rgb), .42);

字重正規化

Zen Kaku 只有 300/400/500/700/900，沒有 600 也沒有 800。改動前有 82 處使用這兩階，全部由瀏覽器合成（模糊、失真）。

「+1」和「+5」是 FocusSession.vue 的，它在第一次掃描範圍外，由 code review 抓出。

數字對齊補償

這是 code review 抓到最嚴重的問題。 --cd-font-mono 現在指向比例字體，但那 38 個使用點幾乎都是垂直堆疊的時間和日期數字 —— 時間刻度、時間下拉、日期格、各 agenda 的時間欄。比例字體下 11:30 和 12:00 寬度不同，整欄會參差。 而且全專案零個 tabular-nums，沒有任何補償。

修法：新增 --cd-numeric-aligned: tabular-nums，38 個點位全部加上 font-variant-numeric。 Zen Kaku 有等寬數字，所以對齊保住了，不需推翻兩種字體的決定。
唯一刻意改變外觀的地方：月份標題從 800 44px 無襯線變成 italic 400 44px 義大利襯線， 因為 Instrument Serif 只有一個字重。這是整次改動中唯一預期渲染會不同的地方。

字級：實測現況

2026-07-31 調整後的實際值 · 逐一實測自 src/components/**

All-day 標籤8px11px反而壓低一階 —— 見下方說明
兩個「不能跟著放大」的例外，值得記住。

1. All-day 標籤壓在 11px。它是 7 個字元，而時間軸左欄是固定 50px。 跟著放到 12.5px 會需要約 45.5px，扣掉 padding 後溢出。 它是靜態文字不是需要對齊的數據，所以壓低一階是正確取捨 —— 要維持同尺寸就得加寬左欄，那會推移整個網格。

2. 時間軸事件區塊在高度不足 38px 時隱藏時間行。 16px 標題加時間行需要約 40px，但 30 分鐘的事件只有約 20px 高。 改成拉高 min-height 的話，短事件會互相重疊 —— 所以讓時間行在放不下時退場。
一個容易踩的陷阱：CdMonthGrid 在 JS 裡鏡射了這些尺寸。 它用 CELL_METRICS 常數（格子 padding、日期圓圈高、晶片高、間距）計算每格放得下幾個事件。 改 CSS 而不同步這些常數，計算會靜默失準 —— 不會報錯，只會算錯，導致溢出或空白。

目前值：桌機 { cellPad: 16, headGap: 3, headH: 26, chipH: 21.5, chipGap: 2 }， 手機 { cellPad: 6, headGap: 1, headH: 22, chipH: 22, chipGap: 2 }。 已驗證兩個斷點都仍容納 3 個晶片。

防護機制

npm run check:tokens —— 唯一的自動化接縫。

為什麼是靜態檢查而不是單元測試

這次改動改的是「值怎麼被引用」，不是「渲染出什麼」。 好的測試該斷言外部且持久的性質（沒有硬寫色值殘留）， 而不是斷言「某元素的 background 是某值」—— 後者是測實作細節，每次合理改樣式都會壞。

元件渲染測試被明確否決：測試環境不做 CSS cascade 解析， getComputedStyle 拿不到 var() 解析後的值 —— 會變成「看起來有測但其實沒測到」。
