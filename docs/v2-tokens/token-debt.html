v1 Token 缺口

切換右邊的開關，看哪些東西會變、哪些卡住不動
怎麼用這一頁。上面的開關只做一件事：改掉 :root 裡那組 --cd-* 的值。這就是「切換 token」的全部動作。

每一節左邊是已經吃 token 的樣子（會跟著變），右邊是現在程式碼實際的樣子（卡住不動）。右邊那些就是要修的東西。

「另一組 token」只是用來讓差異看得見的測試值，不是提案配色。你之後要換什麼色都行 —— 重點是機制能不能動。

4項目 B：raw rgba —— 對改名隱形的那 17 處

這是我排在第一優先的原因：它們沒有名字可以搜。

為什麼叫「隱形」。假設你要找出所有用到 olive 的地方，你會搜 --cd-olive。

rgba(179, 172, 145, 0.5) 不會出現在結果裡。它跟 olive 沒有任何文字上的關聯，只是三個數字剛好等於 #B3AC91 的 RGB。

同樣的問題也發生在 scrim：9 處 rgba(40, 38, 30, α)，搜 --cd-scrim 一樣搜不到。

7另外三個平行的顏色來源

這個不解決的話，切 token 只會切一半。

除了 cadence-tokens.css，還有三個地方各自寫了同一組顏色：
  • src/css/app.css:55-71 — Tailwind @theme，15 個顏色（含 --color-btn: #B3AC91）
  • src/css/quasar.variables.sass — Sass 變數，同樣 15 個（含 $btn: #B3AC91）
  • src/composables/use-theme.ts — 四象限色 + 四個配對文字色（#4A3318、#2A2D27、#3E3845、#33403A）

前兩個檔都有明寫「manually kept in sync」的註解 —— 作者知道這是重複，但 Tailwind 和 Sass 需要 build-time 的值，讀不到 runtime 的 CSS 變數，所以無法直接引用。

後果：切換 token 時，Tailwind utility class 和 Quasar 元件會留在舊配色。這需要獨立設計，可以先標記為已知限制，不一定要擋住第一版。

use-theme.ts 那四個配對文字色比較特殊：它們在 CSS token 層完全不存在，只活在 TypeScript 裡。這四個必須先補進 token 層，否則四象限的文字色永遠無法跟著切換。

結論：顏色的部分是小工程，兩到三天。真正花時間的是非顏色那六個族群，而且花的是「你做決定」的時間，不是「我改程式」的時間。

我建議先做最上面三列（合計約 47 處，半天，不改任何像素）。做完之後 olive 和 scrim 就真的能靠切 token 全換掉 —— 那是整件事裡「證明機制可行」的最小可驗證單位。看到它真的能動，再決定要不要往下走。
一個要先講的已知限制：就算顏色全部修完，只要三個平行來源還在，Tailwind utility class 和 Quasar 元件仍會留在舊配色。 這不會擋住第一版，但上線那天會被看到，所以現在就該知道。
